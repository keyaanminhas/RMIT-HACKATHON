# NeutralVault — MVP Specification

> **Challenge:** RMIT Hackathon 2026 — Challenge 2, *Build Without Blind Trust (Vibe Coding with TideCloak, Unlocked)*
> **Core question:** *What could you build if no single party had complete control?*
> **This document:** the complete, detailed feature spec for the NeutralVault MVP. Logic/functionality is built by Kiro; **UI is generated by GPT** against the component contract in §9.
> **Deadline:** 22 Oct 2026, 6:00 PM MYT — functional MVP target **5:00 PM**, last hour reserved for summary + video + submission.
> **Authoritative source:** `brief/neutral-vault-idea.pdf`. Mapping + resources: `RESOURCES.md`.

## 1. One-paragraph product definition

NeutralVault is a **shared scam / mule-account intelligence pool** for banks, telcos and e-wallets.
Members pool fraud signals so everyone catches mules faster — but **the operator running the server is
removed as a trusted party**. Reports are encrypted in the browser, so a host that dumps its own
database sees only ciphertext. Reading another member's *evidence* requires an **M-of-N approval from
distinct organisations** (no self-approval, time-limited). Admitting a new member or changing the
sharing rules requires a **majority governance vote**. Every action is written to a public audit log.
Encryption + collective governance replace the trusted middleman.

## 2. The trust constraint (why this challenge, in one place)

| Lens (from the brief) | NeutralVault's answer |
|---|---|
| **Privacy** — who can access sensitive info? | Reports are AES-GCM encrypted client-side; only authorised roles decrypt. |
| **Custody** — who controls protected data? | The host stores only ciphertext + keyed hashes; it holds no usable key. |
| **Authority** — who may approve important actions? | Tier-2 disclosure and governance both need a distinct-org quorum — no unilateral action. |
| **Trust** — what if a single party can't be trusted? | The "operator dumps the DB" demo yields gibberish; "admin self-grants" is blocked. The system is correct even if the operator is hostile. |

**The swap test (why TideCloak specifically):** with a normal IdP plus a DB-held key, the operator
holds the key and the "dump the database" moment fails. TideCloak keeps the encryption key and the
hash key **unreadable to the host**, which is the single fact that makes the demo *true* instead of theatre.

## 3. Actors & roles

| Role | Who | Can do |
|---|---|---|
| **Member analyst** | Bank A, Bank B, Telco, E-wallet staff | File reports, run tier-1 checks, file tier-2 disclosure requests, decrypt evidence they're authorised for |
| **Approver (org officer)** | One officer per member org | Approve/deny tier-2 requests and governance proposals *for their own org* |
| **Operator** | The company hosting the server | Runs infra; **holds only ciphertext**; cannot read evidence, cannot self-grant access |
| **Prospective member** | A new org applying to join | Admitted only by a successful governance vote |

Login is **BYOiD via TideCloak** — each analyst signs in with their own identity; there is no shared
master account and no password database for the host to steal.

## 4. Data model

All persistent records hold **no plaintext PII**. Account identifiers are stored as keyed hashes.

```
Org            { id, name, kind: "bank"|"telco"|"ewallet", isMember: bool, approverUserId }
Report         { id, orgId, acctHash, reasonCode, severity,
                 evidenceCipher, evidenceIv, createdAt }           // evidence = ciphertext only
DisclosureReq  { id, reportId, requesterOrgId, requesterUserId,
                 status: "pending"|"approved"|"denied"|"expired",
                 approvals: [{orgId, userId, at}],                 // distinct orgs only
                 grantedAt, expiresAt }
Proposal       { id, kind: "admit_member"|"change_rule",
                 payload, status: "open"|"passed"|"rejected",
                 votes: [{orgId, userId, choice: "yes"|"no", at}] }
AuditEntry     { id, ts, actorOrgId, actorUserId, action, targetId, detail }
```

- **`acctHash`** = `HMAC-SHA256(hashKey, normalise(accountNumber))`. The `hashKey` is itself encrypted
  and only member roles can decrypt it, so a DB dump reveals neither account numbers nor the key.
- **`evidenceCipher`/`evidenceIv`** = AES-GCM 256 output. The host never receives the symmetric key.

## 5. Core features (functional spec)

Each feature lists its trigger, exact rules, and the audit entry it must write.

### F1 — BYOiD login (TideCloak) — *MUST*
- **Trigger:** user opens the app unauthenticated.
- **Behaviour:** redirect to TideCloak; on return, the app knows the user's org + role from token claims.
- **Rules:** no app-held password; role/org come from verified token claims, never from client input.
- **Audit:** `login` (actor, org).

### F2 — File a mule report (encrypt-on-submit) — *MUST*
- **Trigger:** member analyst submits { account number, reason code, severity, free-text evidence }.
- **Behaviour:**
  1. `acctHash = HMAC(hashKey, normalise(accountNumber))`.
  2. `evidenceCipher = AES-GCM(key, evidence)` — encryption happens **in the browser**.
  3. Store `{orgId, acctHash, reasonCode, severity, evidenceCipher, evidenceIv}`. Plaintext account
     number and evidence are **never** persisted.
- **Rules:** only a member org may file. Reason code from a fixed enum (see §6).
- **Audit:** `report_filed` (actor org, acctHash prefix, reasonCode).

### F3 — Tier-1 check (hit / no-hit + metadata) — *MUST*
- **Trigger:** any member analyst enters an account number to check.
- **Behaviour:** hash the input the same way, match against `acctHash`. On a hit, return
  **reason code + severity + reporting org + date** — but **NOT the evidence**.
- **Rules:** returns metadata only; evidence stays sealed. No-hit returns a clean "not found".
- **Audit:** `tier1_check` (actor org, acctHash prefix, hit/miss).

### F4 — Tier-2 disclosure request — *SHOULD*
- **Trigger:** an analyst who got a tier-1 hit requests the underlying evidence.
- **Behaviour:** creates a `DisclosureReq` in `pending`; routes to approvers.
- **Rules:** requester's own org cannot be one of the approvers.
- **Audit:** `tier2_requested` (requester org, reportId).

### F5 — M-of-N approval from distinct orgs — *SHOULD*
- **Trigger:** an approver acts on a pending request.
- **Behaviour:** records an approval; when approvals from **N distinct organisations** are reached
  (default **M-of-N = 2** distinct orgs), status → `approved`, `grantedAt = now`, `expiresAt = now + 30 min`.
- **Rules (enforced, each independently demoable):**
  - **No self-approval** — an approver from the requester's org is rejected.
  - **Distinct orgs** — two approvals from the same org count once.
  - **One approval per org** — re-approval by the same org is a no-op.
  - **Must include the reporting org** — the org that filed the report is a required approver.
- **On approval:** the requester (and only the requester) can decrypt the evidence until `expiresAt`.
- **Audit:** `tier2_approved` / `tier2_denied` (each approver org), `tier2_granted` (on quorum).

### F6 — Time-limited evidence decryption — *SHOULD*
- **Trigger:** approved requester opens the evidence.
- **Behaviour:** decrypt `evidenceCipher` client-side and display; after `expiresAt` the decrypt path
  refuses and the UI shows "access expired".
- **Rules:** decryption is gated by *both* approval state and the clock.
- **Audit:** `evidence_viewed` (actor org, reportId), `access_expired` when the clock blocks it.

### F7 — Governance vote (admit member / change rule) — *COULD*
- **Trigger:** a member opens a proposal (`admit_member` for a prospective org, or `change_rule`).
- **Behaviour:** member orgs cast yes/no; when **majority of current member orgs** vote yes, status →
  `passed` and the effect applies (prospective org's `isMember = true`, or the rule changes).
- **Rules:** one vote per org; only current members vote; majority of member orgs (not of votes cast).
- **Audit:** `proposal_opened`, `vote_cast` (per org), `proposal_passed`/`proposal_rejected`.

### F8 — "No admin self-grant" guard (breach theatre) — *MUST (demo)*
- **Trigger:** an operator/admin attempts to grant themselves decrypt access directly.
- **Behaviour:** the action is **rejected** — access can only come through F5 (quorum) or F7 (vote).
- **Audit:** `self_grant_blocked` (actor).

### F9 — Operator DB dump → ciphertext (breach theatre) — *MUST (demo)*
- **Trigger:** a "Dump database (operator view)" button.
- **Behaviour:** shows the **raw stored records** exactly as the host sees them —
  `acctHash`, `evidenceCipher`, `evidenceIv` — i.e. gibberish, no plaintext anywhere.
- **Audit:** `operator_dump` (actor = operator).

### F10 — Public audit log — *SHOULD*
- **Trigger:** anyone opens the Audit page.
- **Behaviour:** reverse-chronological list of every `AuditEntry` with ts, actor org/user, action,
  target, detail. Append-only in the UI; entries are never edited or deleted.
- **Audit:** reading the log writes nothing.

## 7. Seed data (synthetic, for the demo)

- **Orgs:** `Bank A` (member), `Bank B` (member), `Telco One` (member), `E-Wallet Co` (**prospective** — admitted live in F7).
- **Reports:** 3–5 pre-seeded mule reports across Bank A / Telco One with varied reason codes & severities,
  so Bank B gets an immediate tier-1 hit in the demo.
- **Users:** one analyst + one approver per member org; one operator account.
- All data is clearly labelled synthetic; **no real account numbers or PII**.

## 8. What is real vs simulated (must be stated in the submission)

| Component | Status | Note |
|---|---|---|
| **AES-GCM evidence encryption** | **Real** | Browser `crypto.subtle`; the "dump → ciphertext" beat is genuinely true. |
| **HMAC keyed-hash account matching** | **Real** | `crypto.subtle` HMAC-SHA256. |
| **BYOiD login** | **Real where the TideCloak node is up** | `@tidecloak/react`, `configUrl=/tidecloak.json`. |
| **M-of-N quorum, no-self-approval, expiry** | **Simulated in-app** | Enforced by `vault.js` reducer, not by a Tide-enforced policy (Forseti policy is the production target). |
| **Governance vote effect** | **Simulated in-app** | Vote tally + rule application is local state. |
| **Cross-org decrypt / app-facing quorum API** | **Unverified in TideCloak beta** | Flagged in the idea PDF; record a backup video. |

**Honesty note for judges (from the idea PDF):** a member insider holding the hash key could brute-force
low-entropy account numbers. Stated openly; **private set intersection** is named as the roadmap fix.

## 9. Architecture & component contract (the boundary GPT builds against)

**Stack:** Vite + React 19 + `@tidecloak/react@0.14.33`. Single-page app.

**Logic modules (Kiro — pure, UI-agnostic, no JSX):**
```
src/crypto.js    AES-GCM encrypt/decrypt, HMAC account hashing, key handling
src/vault.js     reducer + action creators: report, tier1Check, requestTier2,
                 approve, decryptEvidence, openProposal, vote, operatorDump, audit
src/config.js    M-of-N, accessTTL, reason codes, severities
src/seed.json    synthetic orgs / users / reports
```

**UI layer (GPT — presentation only, imports from the modules above):**
```
src/App.jsx      composes the screens; holds no business rules
components/       LoginBar, ReportForm, CheckPanel, DisclosureInbox,
                 EvidenceView, GovernancePanel, OperatorConsole, AuditLog
```

**Contract rule:** every business rule lives in `vault.js`/`crypto.js` and is covered by the actions
listed in F1–F10. `App.jsx` and components call those actions and render their results — they must
contain **no** encryption, quorum, expiry or vote logic. This lets GPT restyle freely without being
able to break a security rule.

**State shape (single reducer store):**
```
{ session:{user,org,role}, orgs[], reports[], requests[], proposals[], audit[], now }
```

## 10. Screens (what the UI must expose)

1. **Login bar** — BYOiD sign-in; shows current org + role.
2. **Report** (F2) — account #, reason code, severity, evidence → "Encrypt & file".
3. **Check** (F3) — account # → hit card (reason, severity, reporting org, date) or "no record".
4. **Disclosure inbox** (F4–F6) — my requests + requests awaiting my org's approval; approve/deny;
   on-grant evidence view with a live expiry countdown.
5. **Governance** (F7) — open proposals, per-org vote buttons, live tally, "admit E-Wallet Co" demo.
6. **Operator console** (F8–F9) — "Dump database" (shows ciphertext) + "Self-grant access" (blocked).
7. **Audit** (F10) — full append-only log.

## 11. TideCloak setup (install + wire)

Dependency already declared in `app/package.json` (`@tidecloak/react@^0.14.33`) and installed.

**Local dev node (Docker):**
```bash
docker run -d -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=password \
  tideorg/tidecloak-dev:latest
```
1. Open the admin console (`http://localhost:8080`), create the realm/app.
2. Set the redirect URIs to the Vite dev origin (`http://localhost:5173`).
3. Create roles per org (analyst, approver) and the encrypt/decrypt tags.
4. Download the client config to `app/public/tidecloak.json` (consumed by `main.jsx`'s
   `TideCloakContextProvider configUrl="/tidecloak.json"`).

**Graceful fallback:** if `tidecloak.json` is absent, the app runs in a labelled **"Demo identity"**
mode (pick an org/role from a dropdown) so the functional demo never hard-blocks on the node being up —
but the submission states login is real when the node is present.

## 12. Run instructions

```bash
cd app
npm install          # installs @tidecloak/react, react, vite
npm run dev          # http://localhost:5173
# optional: start the TideCloak Docker node (above) and drop tidecloak.json into public/
```
